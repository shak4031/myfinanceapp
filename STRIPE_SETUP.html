MYFINANCE / ADMINISTRATOR SETUP GUIDE / UPDATED OCTOBER 24, 2026

Enable Stripe payments, step by step

Connect MyFinance to Stripe, configure your server, test subscriptions safely, and move to live payments when you are ready.

Where this work happens: Stripe Dashboard, your hosting provider's backend environment settings, and a separate staging copy of MyFinance.

Start in a sandbox. Keep secrets out of this document.

All example values are placeholders. Enter real credentials only in your hosting provider's secret manager. Never paste keys into WordPress, browser code, chat, or source control.

Keep ALLOW_REGISTRATION=false on the deployment being configured until checks pass. This closes public signup; it does not stop existing subscriptions or invited users.

1. Confirm plans and trial behavior

One subscription covers the entire household, including invited members. Pricing is not per login or per imported bank account.

Monthly household plans
PlanPriceIncludes
BasicUSD $9.99/monthAccounts, statement imports, transactions, categories, and everyday dashboard.
ProUSD $14.99/monthBasic plus analytics, budgets, debt planning, and savings goals.
  • Eligible households receive a 15-day Pro trial, even when Basic is selected for renewal.
  • The trial begins after verified email, explicit billing consent, and completed Stripe Checkout with payment details. Account creation alone does not start it.
  • Stripe automatically bills the selected plan when the trial ends unless canceled.
  • Cancellation preserves access through the trial or paid period; it does not delete transaction data.
  • The app attempts an owner-only reminder email 24 hours before trial expiry.
  • A used trial cannot restart for the same household. Unrelated accounts using different emails are not currently linked for person-level trial-abuse prevention.

2. Set up Stripe

A. Create or select a sandbox

  1. Sign in to Stripe Dashboard.
  2. Create or select a sandbox for testing. Use a separate staging app and database.
  3. Keep the API key, products, prices, and webhook destination in that same Stripe environment.

Business verification and payout-bank setup must be completed before live payments.

B. Create two products and monthly prices

In Product catalog, create these active, fixed recurring prices:

ProductPrice settingsCopy its Price ID to
MyFinance BasicUSD 9.99, every 1 month, quantity 1STRIPE_BASIC_PRICE_ID
MyFinance ProUSD 14.99, every 1 month, quantity 1STRIPE_PRO_PRICE_ID

Use IDs beginning price_, not Product IDs beginning prod_. Do not use annual, metered, or tiered pricing. The app sets the trial in Checkout; you do not need a product-level trial.

Tax collection is not configured by these steps. Review your obligations before launching.

C. Obtain your server API key

Open API keys in the selected sandbox. Put the secret key, beginning sk_test_, in the server variable STRIPE_SECRET_KEY.

The current Stripe-hosted Checkout integration does not require a frontend publishable key. A restricted server key needs separately validated permissions for customers, prices, subscriptions (including metadata updates), subscription schedules (create/read/update/release), Checkout, and billing-portal operations.

D. Create a webhook destination

In Workbench / Webhooks, create an event destination for your account, using:

POST https://YOUR_APP_DOMAIN/api/billing/webhook

Select all eight events:

checkout.session.completed
checkout.session.expired
customer.subscription.created
customer.subscription.updated
customer.subscription.deleted
customer.subscription.trial_will_end
subscription_schedule.created
subscription_schedule.updated
subscription_schedule.released
subscription_schedule.completed
subscription_schedule.canceled
subscription_schedule.aborted
invoice.paid
invoice.payment_failed

Copy that destination's signing secret, beginning whsec_, into STRIPE_WEBHOOK_SECRET. It is different from the API key.

  • The endpoint must be public over HTTPS, without hosting login protection or a CAPTCHA.
  • Route it to the Node backend, not a static frontend fallback.
  • The proxy must preserve the raw request body and Stripe-Signature header.
  • Valid processed events return HTTP 200. Unsigned requests should return 400.

E. Review customer-facing settings

Configure business branding, support email, statement descriptor, receipts, and relevant policy links. Review payment-failure emails and refund/cancellation terms.

The app creates its own portal configuration when an owner opens billing. It supports cancellation at period end, payment-method updates, invoices, and customer email/address updates. Active Basic owners without scheduled cancellation can choose Upgrade to Pro in Stripe: Stripe confirms an immediate prorated charge without changing the renewal date. Pro access waits for a verified webhook and paid upgrade invoice.

Pro → Basic at next renewal: The owner explicitly agrees in app billing to Basic at USD 9.99/month starting on the displayed renewal date. Pro remains available until then, including the full original trial for Pro-selected trials. No immediate charge, proration, or data deletion occurs. Basic and Pro are separate Stripe products, so this uses subscription schedules rather than assuming the portal supports same-product scheduled downgrades. The current Pro phase and trial end are preserved, followed by one bounded Basic month and release to ongoing Basic. Billing displays the pending date; Keep Pro removes the downgrade and retains USD 14.99/month renewal. Remove a pending downgrade before opening Stripe to cancel. Members cannot change billing. Subscription and schedule webhooks retrieve current state; reminders use pending Basic pricing.

In the sandbox, verify renewal/trial-expiry timing, unchanged Pro before transition, Basic reminder pricing, lost-response retries, duplicate confirmation, Keep Pro and rescheduling, owner/member restrictions, cancellation conflicts, and retained financial records after Basic starts. Automated tests use fakes; real sandbox verification is a separate launch check.

3. Configure and restart your server

A. Prepare the deployment

  1. Back up PostgreSQL and verify a restore. Use an isolated staging database, not production, for testing.
  2. Deploy the version containing household billing and the latest resubscription/webhook fixes.
  3. From the application root, run the commands below in development/CI or staging:
npm ci
npm test
npm audit --omit=dev

On Windows PowerShell, use npm.cmd if execution policy blocks npm.ps1. The Stripe SDK is already in the lockfile.

Launch blocker: The last recorded dependency audit reported 17 advisories, including two critical. Run a fresh audit, remediate, and regression-test fixes before public launch. Do not apply major-version upgrades blindly.

B. Set backend environment variables

Use your hosting service's Environment / Secrets settings for the Node backend. The app does not read this guide or automatically load a .env file through npm start.

Additional deployment-specific settings:

  • DATABASE_SSL=true when your provider requires certificate-verified database TLS. Do not disable certificate validation.
  • TRUST_PROXY_HOPS must match your actual trusted reverse-proxy hop count. Do not blindly copy a value.
  • PORT should use the platform-assigned port; the app defaults to 3000 and binds to 0.0.0.0.
  • Preserve AUDIT_HASH_SECRET and existing monitoring/retention settings.
  • OWNER_SETUP_TOKEN is for first-time owner setup only. Do not recreate the administrator to enable Stripe.

There is no separate STRIPE_ENABLED switch. Allow outbound HTTPS to Stripe and connections to your SMTP server. Apply consistent settings to every backend instance.

C. Restart through your hosting provider

npm start
# Equivalent: node backend/server.js

Restart/redeploy the supervised service rather than launching a second unmanaged copy. Startup runs database migrations; the connection must have the documented table/role migration privileges.

Check for Private account schema ready and MyFinanceApp listening on port in startup logs. Investigate failures rather than ignoring them.

Keep one server instance always running. The reminder worker starts automatically and checks every minute. Sleeping or scale-to-zero hosting can delay reminders. No separate cron job is required; database locks coordinate active instances.

D. Confirm readiness

Sign in as a household owner and open Settings > Billing. An authenticated GET /api/billing should return configured=true and owner=true.

This checks setting presence only. It does not prove the credentials, price configuration, email delivery, or webhook connectivity work. Complete the tests below.

4. Test the complete payment flow

Use a fresh unpaid household owner, not administrator user 1, the public demo, or a grandfathered manual paid account. Temporarily enable registration only in isolated staging and restart it to test signup. Keep live signup closed.

  1. Signup and verification: Select Basic, create the account, and confirm the plan is retained. Receive the verification email. Checkout must remain blocked before verification.
  2. Checkout consent: Verify the email and accept the recurring-billing disclosure. Stripe should show the trial and selected renewal price.
  3. Sandbox card: Use 4242 4242 4242 4242, any future expiry, and any three-digit CVC. Use only in sandbox/test mode, never with real card data.
  4. Activation: Confirm successful HTTP 200 webhook deliveries in Stripe. The app should grant Pro trial access even for a Basic renewal plan. A success redirect alone must not grant access.
  5. Cancellation: Cancel through the owner's Stripe portal. Trial access should continue until expiry, then lock, without paid conversion.
  6. Paid conversion: Validate Basic and Pro conversions and invoice outcomes. Basic should lose advanced features after its trial; Pro should retain them.
  7. Failure and recovery: Use Stripe-documented sandbox failure scenarios. Past-due/unpaid access should lock; successful current-period payment synchronization should restore eligible access. Billing and authentication must remain available.
  8. Returning customer: Sign in after a canceled trial. No second trial should be offered. Paid activation is required and prior records should remain intact.
  9. Household permissions: Invite another login. Members share their household's records and entitlement but cannot manage billing. An unrelated household must not see that data.
  10. Reminder: Verify a real owner-only email around 24 hours before the actual trial deadline with the server running. Monitor failures and delivery.
  11. Retries: Repeated checkout clicks must not create multiple subscriptions. Duplicate/reordered events must not overwrite current paid access with retired subscription state.
Time simulation is not automatic. The app does not attach Checkout customers to Stripe Test Clocks. Advancing a Stripe clock does not advance the app's system time or reminder worker. Test-clock orchestration needs additional setup/code; otherwise use supported Stripe testing workflows and actual sandbox lifecycle events.

Existing automated regressions use simulated Stripe and email. They are not proof of real processor charging or SMTP delivery.

5. Switch to live payments

Proceed only after sandbox acceptance, dependency remediation, production security review, and review of business verification, tax obligations, privacy notice, automatic-renewal disclosures, refund/cancellation policy, and support details.

  1. Create Basic and Pro products/prices again in live mode, at the exact USD monthly amounts.
  2. Create a live webhook destination for the production URL with the same eight events.
  3. Set production STRIPE_SECRET_KEY to the live secret, and replace both Price IDs and STRIPE_WEBHOOK_SECRET with matching live values.
  4. Keep sandbox credentials and destinations on staging only. Do not mix environments.
  5. Restart production and confirm configuration and webhook delivery. Any real-money smoke test requires explicit authorization; live mode can charge actual money.
  6. Set ALLOW_REGISTRATION=true and restart only when ready to accept new customers.
Changing application settings does not cancel Stripe subscriptions. Never use sandbox keys as a casual rollback for an existing live billing deployment. Live subscriptions can continue charging in Stripe. Stop or change them explicitly in Stripe and reconcile app state if necessary.

6. Troubleshooting

Billing is not configured
Check all four Stripe variables, SMTP_HOST, and SMTP_FROM on the backend process. Restart after changes.
Price does not match the published plan
Verify active fixed monthly USD prices: Basic 999 cents, Pro 1499 cents, interval count 1. Use Price IDs, not Product IDs, and do not mix sandbox/live values.
Invalid webhook signature
Check the destination's signing secret, raw body, signature header, environment, and server clock. Unsigned browser requests are expected to fail.
Webhook gets HTML, redirects, 401, 403, or 404
Check HTTPS, deployment protection, reverse-proxy routing, and the exact webhook path. Stripe cannot authenticate through your hosting login.
Checkout completed but access is locked
Inspect event deliveries and billing.webhook_failed logs. Fix failures and retry delivery; never manually grant access based only on the success URL.
Existing paid account refuses Checkout
Primary owner/admin and grandfathered manual access are protected against accidental double billing. Use a fresh synthetic customer for tests. Replacing manual access needs an explicit migration.
Reminder missing or duplicated
Check server uptime, app owner email, timestamps, SMTP delivery, and billing.reminder_failed. Changing only the Stripe receipt email does not change the app reminder address. A crash after email submission but before database commit can cause a retry; delivery is not guaranteed exactly once.
Cannot upgrade Basic to Pro
Use Upgrade to Pro in Stripe inside the app billing panel, not the general management portal. The household must have an active Basic subscription without pending changes or scheduled cancellation. Test the prorated charge, declined payment and webhook delivery before going live. For Pro-to-Basic, explicitly confirm next-renewal Basic inside app billing; remove a pending downgrade with Keep Pro before cancelling.
