MYFINANCE / TECHNICAL SECURITY FRAMEWORK

Security architecture & data protection

A technical account of the safeguards implemented in MyFinance, the information the service processes, and the responsibilities that remain with its operators and users.

Layered protection, clearly defined

MyFinance combines Railway-hosted HTTPS, a private database, encrypted private networking, PostgreSQL TLS as defense in depth, protected deployment secrets/access, application-level token encryption and database-enforced household isolation. The operator confirmed the private database, HTTPS, secrets/access controls and database TLS on 4 November 2026. This is an operator verification statement, not an independent infrastructure audit.

MyFinance does not receive your bank login credentials through its Plaid Link integration and does not implement payments or bank transfers. It does store account metadata, balances and transaction history to provide financial views. Plaid access tokens are encrypted at the application layer; financial records are not field-level encrypted. Database-volume, backup and log-storage encryption remain separate provider controls whose deployment evidence is not recorded in this document. No independent production assessment, SOC 2 report, PCI DSS validation, ISO 27001 certification or penetration test of MyFinance is asserted.

01 / GOVERNANCE

System scope & threat model

MyFinance is a household financial-planning service with a browser client, a Node.js/Express application, and PostgreSQL storage. Customers use individual logins within a shared household. Inputs are optional Plaid bank connections, uploaded statements, and customer-entered planning records. Financial projections are computed by the application; records are not sent to an external AI service for Financial Checkup.

The security objectives are confidentiality between households, authorized access to financial records, integrity of imports and billing decisions, revocable session access, and accountable operational support. Controls address password guessing, stolen database token records, cross-household record access, cross-origin writes, forged webhooks and unauthorized in-app support access.

Residual threats include compromised browsers or servers, malicious or over-privileged infrastructure operators, misconfigured TLS/storage, exposed deployment secrets, software supply-chain vulnerabilities and service disruption. This framework does not eliminate these risks. A stolen valid session or decrypted Plaid token remains sensitive; hashing and encryption are not substitutes for access control.

02 / ARCHITECTURE

Trust boundaries & data flows

  1. The authenticated customer requests a Link token from MyFinance and opens Plaid Link.
  2. The customer authorizes the institution through Plaid's supported authentication flow, which varies by bank. MyFinance's callback receives a public token and institution metadata, not a bank-password field.
  3. The server exchanges the public token using its Plaid credentials. The resulting access token is encrypted before storage.
  4. The server decrypts the access token in memory when calling Plaid's data APIs. Returned accounts, balances and transaction history enter the customer's household workspace.
  5. Verified webhook notifications and scheduled synchronization keep authorized records current. Disconnecting stops future updates; it does not automatically erase past imports.

Statement-import path

Customer file → HTTPS upload → application parser → household-scoped staging/review → PostgreSQL financial records and import recovery data. This path requires no bank login or Plaid connection. A statement may itself contain sensitive identifiers; uploading it is not equivalent to keeping all account information outside MyFinance.

Key custody and lifecycle

PLAID_TOKEN_ENCRYPTION_KEY must decode to exactly 32 bytes. It is supplied through the server environment, not a customer-held key. The token record stores the IV and authentication tag alongside ciphertext; these are not secret. A database-only exposure is materially different from a compromise of both the database and server environment.

The operator has verified production secrets and deployment-access controls on Railway. Application encryption keys and integration credentials are managed as deployment secrets rather than customer-visible inputs. This verification does not specify sealed-variable status, MFA enrollment, a particular vault product or an automatic rotation schedule; those require their own evidence.

Plaintext tokens exist transiently in server memory for API calls. This is not end-to-end encryption or zero-knowledge storage. The current application does not demonstrate automatic KMS-backed rotation, envelope encryption or a user-key recovery scheme. Operators must protect environment access and back up keys securely. Changing the key without re-encrypting existing tokens makes those connections unreadable.

Encryption at rest is layered

Token encryption protects one specific field. PostgreSQL financial fields, import-recovery data and operational metadata are not encrypted by this application at the column level. Encrypted database volumes, snapshots, backups, log storage and exports must be configured and verified with the hosting provider. Disk encryption protects storage media; it does not stop an authorized running database or server from reading records.

05 / CHANNEL PROTECTION

Transport security & TLS

The production service is hosted on Railway, with HTTPS confirmed by the operator. Railway provisions and renews public endpoint certificates. Application production startup requires an HTTPS APP_ORIGIN; production responses send HSTS with max-age=31536000, and session cookies use Secure. The exact negotiated TLS versions and cipher suites are not recorded here and are not inferred from those application settings.

Private database and defense-in-depth transport

The operator has verified that PostgreSQL is private rather than publicly exposed and that database TLS is enabled as an additional transport safeguard. Railway documents encrypted WireGuard tunnels for service-to-service communication within a project environment, using cryptography including ChaCha20, Curve25519 and BLAKE2s. Network encryption and PostgreSQL TLS protect different layers; neither replaces database authentication or household authorization.

Cipher suites: baseline, not a claim about a live handshake

For TLS 1.3, a modern endpoint may negotiate TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384 or TLS_CHACHA20_POLY1305_SHA256. TLS 1.2 should prefer forward-secret ECDHE key exchange with AEAD ciphers such as AES-GCM or ChaCha20-Poly1305. These are recommended infrastructure settings, not suites pinned or verified by this Express source. The certificate's authentication algorithm, ephemeral key-exchange group and negotiated record cipher are separate properties.

Recheck the public endpoint and database transport after domain, certificate, connection-string or infrastructure changes. Development HTTP on localhost is not equivalent to this production configuration. TLS protects traffic between endpoints; it does not prevent the endpoints themselves from reading it.

06 / IDENTITY

Authentication & session lifecycle

Authentication uses email/password credentials and server-side opaque sessions, not a client-provided user ID or a browser-stored authorization JWT. New passwords must be 12 to 128 characters. Login and reset attempts are limited using email/IP-derived keys; invalid logins and lockouts are audited. Password reset responses avoid directly confirming whether an email is registered.

  1. After successful credential verification, the server issues a random session token and stores its SHA-256 digest.
  2. The browser receives a finance_session cookie with HttpOnly, SameSite=Strict, Path=/ and Secure in production. HttpOnly prevents ordinary JavaScript reads of the cookie; it does not make an XSS-compromised page harmless.
  3. Each authenticated request validates the session in privileged storage. The session expires after 10 minutes without user interaction or after a 12-hour absolute lifetime, whichever occurs first. Background requests do not renew inactivity.
  4. Logout and completed password resets revoke server-side sessions. Browser session guards hide private views and discard stale responses after lock/sign-out.

Password reset tokens are hashed, single-use and valid for 30 minutes. Registration verification links are hashed, single-use and valid for 24 hours. Email-bound household invitations are hashed, single-use and valid for 48 hours. Historical accounts grandfathered as verified are not retrospective evidence of email verification. Protect email accounts: a mailbox is part of the recovery trust boundary.

Explicitly trusted browsers: ninety-day recognition

After successful MFA verification, users may choose Trust this browser for 90 days. This choice is unchecked by default and does not apply to new or unrelated browsers. Passwords remain mandatory. The browser holds a random 256-bit token in an HttpOnly, SameSite=Strict, host-only cookie, Secure with the __Host- prefix in production. PostgreSQL stores its SHA-256 hash, login ID and timestamps, not a raw token or device fingerprint.

Trust has a fixed ninety-day expiry and the token rotates on each trusted sign-in without extending that date. Up to twenty browsers can be remembered per login. The trust cookie alone grants no financial API access and does not change ten-minute inactivity or twelve-hour session limits. Clearing cookies, expiration or revocation requires MFA again; normal sign-out preserves trust.

Settings lists remembered browsers and offers revocation of all trust plus other active sessions. Password changes/resets, MFA enrollment confirmation, disabling MFA, recovery-code replacement and administrator session revocation invalidate trust. Security trade-off: a stolen trust cookie together with a stolen password can bypass the MFA prompt. Never trust public/shared devices. This is cookie-based browser recognition, not hardware attestation, phishing-resistant authentication or a bank-style risk-scoring engine.

State-changing browser API calls must have the configured same-origin Origin. Signed provider webhooks follow their own authentication flow. API responses use Cache-Control: no-store. Anti-framing and MIME-sniffing headers are also set. No-store does not guarantee removal of every browser, operating-system or infrastructure copy.

Optional authenticator MFA and recovery

Individual logins can enable TOTP MFA in Settings & support after confirming their password and an authenticator code. On untrusted browsers, enrolled logins require both the password and a valid authenticator or recovery code before a sign-in session is issued. An explicitly trusted browser instead presents its password and valid remembered-browser cookie. Enrollment signs out other devices. This feature requires a separately configured server encryption key; it is optional rather than enforced across all customers or administrators.

TOTP uses HMAC-SHA-1 with a random 160-bit secret, six digits and 30-second periods for broad compatibility with standard authenticator apps, including Google Authenticator and Microsoft Authenticator. Scanning the enrollment QR imports settings automatically; manual entry uses standard time-based SHA-1 defaults. The enrollment URI specifies algorithm=SHA1. The server generates the PNG QR locally without an external QR service and returns it only in the authenticated, no-store enrollment response. QR and manual key encode the same private secret and are removed from the page on confirmation or session reset; never share or screenshot them. Verification uses this single algorithm, not a try-both fallback. The accepted clock window is one period before/after the current step; successful time steps cannot be replayed. Secrets and ten-minute pending enrollment records are AES-256-GCM encrypted under MFA_ENCRYPTION_KEY, with the user ID bound as authenticated associated data.

Algorithm context: SHA-1 is deprecated for digital signatures and collision-sensitive hashing. Known SHA-1 collision attacks do not directly break the keyed HMAC-SHA-1 construction used for TOTP. Its use here is limited to short-lived authenticator codes with rate limits and replay prevention; session tokens and recovery codes continue to use SHA-256 hashing. This is not an endorsement of SHA-1 for certificates, passwords or general-purpose signatures.

Enrollment or code replacement returns ten independent 128-bit recovery codes once. Only SHA-256 digests are stored; each recovery code is consumed atomically once. Disabling MFA or replacing recovery codes requires the current password plus a factor. After using a recovery code, the remaining codes still work. If the set may be exposed or is running low, choose Replace recovery codes in Settings with the password and an authenticator code or another unused recovery code. Replacement invalidates every old code and browser trust; save the new set securely. Replacing recovery codes does not restore a lost authenticator. Without an authenticator backup, users must disable MFA with their password and an unused recovery code, then immediately enroll the replacement device.

Password resets preserve MFA. There is no email-only MFA reset. For lost authenticators and recovery codes, administrators can disable MFA after independently verifying the account owner, confirming the target email, and reauthenticating with their own password and factor if enrolled. The server enforces credentials and acknowledgment, not the quality of the operator's identity verification. This audited override removes MFA and old recovery codes, revokes sessions, support grants and browser trust, and attempts a security email; notification failures are surfaced. The existing password remains valid. Users should immediately re-enroll MFA, but re-enrollment and a waiting period are not enforced. Administrator credentials and recovery procedures are therefore part of the MFA trust boundary and must be protected against account takeover and social engineering.

Customers should still save separate recovery codes securely. Demo and support sessions cannot change authenticator settings. Limits: TOTP is not phishing-resistant. No passkeys, hardware-key requirements, device-bound sessions or immunity to browser/session theft are claimed. Implementation of optional MFA does not attest to its adoption by any particular production user.

07 / ACCESS CONTROL

Household isolation & authorization

The server derives the acting login from the validated session and resolves household membership. Client-provided household/user IDs do not select the financial tenant. The immutable tenant key is the household's original owner ID; shared members operate within that workspace using their own logins.

Financial operations execute in a PostgreSQL transaction with SET LOCAL ROLE finance_app_runtime and transaction-local app.user_id. The role is NOLOGIN, NOSUPERUSER and NOBYPASSRLS. Financial tables enable and force row-level security with both read (USING) and write (WITH CHECK) policies. Composite foreign keys prevent cross-household references between transactions and accounts/imports/labels.

Transaction-local context avoids leaking one tenant's identity through a reused pooled database connection. Financial operations recheck current membership. Removing a household member revokes sessions, but an already-authorized read in flight may finish. Household owners alone manage invitations, billing and support grants.

Identity, audit, billing and migration operations use a distinct privileged database path; they require route-level authorization and are not protected by the financial runtime policies. These controls constrain normal application access, not an operator with privileged database access or an attacker controlling the server.

08 / EXTERNAL TRUST

Third-party integration security

Plaid

The integration requests transaction data and retrieves account/balance information. Tokens are exchanged server-side; access tokens are not returned to the financial browser UI. Incoming webhooks require an ES256 signature and a digest matching the raw request body. Repeated notifications can still occur; signature validation is not a guarantee of one-time delivery. Synchronization is applied transactionally.

Disconnecting removes the active bank connection and stops future app updates, while previously imported financial history remains. Refer to Plaid's consumer disclosures for its own data practices. This document describes MyFinance's integration, not every Plaid product, institution practice or provider assurance.

Stripe

Customers enter card information in Stripe-hosted Checkout. MyFinance retains billing identifiers and subscription state, not PAN/CVC. Subscription access is determined by authenticated Stripe webhook processing and current subscription state, never solely by the browser's success redirect. Checkout is not an independent compliance certification of MyFinance.

Public demo

The demo is a shared showcase login with intentionally public credentials and generated sample records. Anyone using that login can see its shared workspace. Never upload personal statements, enter private information or connect a real bank in the demo. Use a separate personal account for real records. A demo login count measures successful sign-ins, not distinct testers or completed testing sessions.

09 / DETECTION & RESPONSE

Monitoring, support & retention

Operational evidence

Authentication outcomes, lockouts, administrator actions and errors carry request IDs and audit records. Audit events are protected against ordinary updates by an append-only database trigger; this is not a cryptographically tamper-evident log or protection against a privileged operator. Logs redact selected sensitive fields, but redaction is not proof that every possible secret or identifier has been removed.

Administrators can inspect account metadata and operational logs. Customer financial access through the support UI requires a customer-approved grant with a reason, expiry and read/write scope. Read-only is the default, enforced at the route layer and by PostgreSQL read-only transactions. Grants last 1 to 72 hours and can be revoked; support requests record actor, subject, grant and outcome. Authorized hosting/database operators still retain infrastructure-level access.

Privacy-minimal traffic reporting

Homepage views and signup clicks are stored as day/event/count aggregates, retained for 365 days by scheduled maintenance. The reporting request omits cookies and sends only an allowed event name. A bounded, transient IP-derived in-memory limiter mitigates casual reporting abuse; no IP is stored in the daily counter. Normal authentication audit records can contain user IDs and hashed email/IP identifiers, and hosting access logs may retain additional network metadata.

The Traffic tab shows UTC calendar-day totals, not unique visitors or a visitor-linked conversion funnel. Scripts blocked by browsers, failed reports, repeated clicks and bots affect accuracy. There is no referrer capture or Reddit attribution. View/click tracking begins when this version is deployed; it cannot reconstruct earlier page traffic.

Retention and deletion

Disconnect, import undo and permanent account deletion are different actions. Undo retains import recovery records. Audit retention is configurable from 30 to 3650 days (365 by default); stored warning/error log retention is separately configurable. Backups, snapshots, exports, third-party records and infrastructure logs need separate retention/deletion procedures. Do not interpret account deletion as immediate erasure of every backup or Stripe billing record.

Report suspected security issues through Contact. Start with a general description and approximate time. Do not send passwords, tokens, full account numbers or unredacted statements. For urgent bank fraud or disputed payments, contact the institution directly. Notification, recovery and regulatory obligations require an operator-run incident process; no automated response-time guarantee is asserted here.

10 / ASSURANCE

Verification & deployment responsibilities

Recorded production verification

On 4 November 2026, the MyFinance operator confirmed the Railway private database, public HTTPS, secrets/access controls and PostgreSQL TLS defense in depth. This document records that attestation alongside source-implemented safeguards. It does not reproduce configuration screenshots, handshake results or access-review records, and does not present operator confirmation as independent certification. Storage/backup encryption, restore testing and specific TLS cipher suites have not been confirmed in this record.

Automated tests cover household isolation, session/support behavior, imports, token cryptography and webhook handling. Embedded database tests exercise policy behavior without using production data. Tests cannot verify a live TLS endpoint, a cloud provider's disk encryption, backup handling or real operator permissions. A source review is not a penetration test.

Ongoing production assurance checklist

  • Maintain the verified HTTPS endpoint and private database; recheck certificate validity, redirects, protocol policy and database exposure after changes.
  • Preserve PostgreSQL TLS certificate validation and encrypted private networking; retain verification evidence.
  • Obtain and record provider evidence for encrypted disks, backups and logs; test recovery without exposing customer data.
  • Maintain verified deployment secrets/access controls; protect key recovery copies and review operator privileges.
  • Review migration/administrative privileges and household RLS policies; minimize privileged access.
  • Check proxy hops, SMTP security/delivery, webhook secrets and alert delivery.
  • Test expiry, logout, reset, membership removal, read-only support and webhook rejection on a non-production environment.
  • Maintain retention/deletion and incident-response procedures; refresh this verification record when production controls change.

Assurance boundary: this document is a transparent security architecture description, not a claim of NIST, OWASP, SOC 2 or ISO certification. No online service can promise zero risk. Evaluate both the implemented controls and the deployed environment before uploading financial information.
